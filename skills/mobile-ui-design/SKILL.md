# 移动端 UI 设计

把用户目标变成可操作、可读、可验证的移动页面。复用设计决策和语义组件，依据项目品牌与平台调整视觉；不要把某个项目的颜色、页面数量或技术栈当成通用要求。

## 先建立项目上下文

检查现有主题、组件、导航、关键页面、资源本地化、状态来源和构建入口；已有截图或运行环境时，先观察真实页面。明确本次是设计建议、局部修改还是整体实现，按用户范围交付。

用已有事实形成一份短设计约定：

- 用户进入页面要理解什么、完成什么；核心内容和主要动作。
- 品牌、现有设计系统与原生平台习惯；哪些是约束，哪些可以调整。
- 实现栈、主题入口、复用组件和涉及的页面。
- 数据、权限、付费、保存/取消、返回和草稿恢复的现有行为。
- 目标设备、语言、字体尺寸和可执行的验收条件。

跨多页面改版时可使用 [项目设计约定模板](assets/project-design-brief.md) 留下决策；小改动在工作记录中说明即可。能从项目推断的内容先推断并标明假设，不为填表逐项询问用户。

## 选择视觉和页面结构

需要制定或调整颜色、字号、间距和组件时，读 [设计语言与主题](references/design-language.md)。优先映射现有 token；品牌缺失或用户希望复用本次清爽绿色时，可采用 [可选主题预设](assets/calm-green.tokens.json)。预设是起点，需要适配品牌、信息密度、字体和对比度。

需要调整首页、列表、配置、设置或付费页时，读 [页面模式](references/page-patterns.md)，只选择项目确实需要的模式。不要为了套模板新增功能、付费墙或导航层级。

区分布局优化与能力扩展：搜索、筛选、统计汇总、预览等示例，仅在项目已有或用户要求时纳入实现。上下文未确认的能力可以作为可选建议列出，不能在方案中悄悄变成已存在的功能或默认实施项。

保留以下交互语义：

- 页面强调主要动作，但不隐藏用户完成任务需要的次要操作。
- 真实状态优先于装饰：未知、过期、空数据、加载、权限缺失、不可用和失败需要能区分。
- 表单布局变化不能改变保存时机、取消语义或丢失草稿；主题切换/旋转后也应成立。
- 价格、解锁、连接、同步成功等声明必须来自实际状态；演示数据应明确标注。
- 分组改善阅读即可；不要为每一行都增加卡片，也不要把所有内容挤进首屏。

## 按现有技术栈落地

读 [平台适配](references/platform-adapters.md) 中对应部分。沿用 Views/XML、Compose、SwiftUI、UIKit、Flutter 或 React Native 的现有组件和状态管理方式；视觉改版本身不要求迁移技术栈、升级构建链或引入大型依赖。

先改共享 token 和少量可复用样式，再验证一个有代表性的页面，随后扩展到此次涉及的页面。保留业务接口、资源 ID、自动化定位和无障碍语义；必要变更同步修改调用处。

对于实现任务，交付实际代码并构建验证；对于设计/评审任务，交付具体布局、状态和组件决策。不要用静态效果图代替要求的真实实现。新工具/API 或随版本变化的行为以项目实际版本和官方文档为准。

## 验证与交付

读 [验证与证据](references/validation.md)，选与改动相关的设备、页面状态和交互组合。先跑项目要求的检查，再验证视觉和真实操作；避免把每种排列组合都机械跑一遍。

保留最终构建对应的截图和简短验收记录：改了什么、实际检查了什么、发现并修复了什么、还有哪些条件未验证。截图必须观察后才能作为验收证据。某个设备或测试账户缺失时，完成其他可执行检查并说明边界，不伪称实机、付款或长期行为已验证。

交付主结论、关键变化、预览/代码位置和验证结果。UI 改版不自动授权上架、发布、真实付款或新增商店商品；已有明确授权按当前任务范围执行。
